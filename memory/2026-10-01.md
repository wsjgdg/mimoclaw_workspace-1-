# 2026-10-01

## 本轮：性能优化（commit 474a07f）——单次扫描 120ms → 1ms

### 定位方法（可复用）
1. 先量化：HTTP 单文件扫描 120~165ms，CLI 只要 2.8ms（其中 1.9ms 是进程启动）
2. **裸 socket 对照**：GET /api/health 只要 0.09ms → HTTP 协议层没问题，是扫描本身
3. **二分隔离**：临时注释掉 `history_add` 再测 → 20.6ms 降到 0.86ms，锁定热点
4. **分步微基准**：`fopen(a)+fputs+fclose` 19ms vs `fopen(a)+fclose` 0.08ms
   → 是**写一次小日志的文件系统延迟**，不是读、不是锁、不是字符串处理

### 三个热点与改法
| 热点 | 原因 | 改法 |
|---|---|---|
| 每次扫描都调 lsof（~97ms） | proc_scan 返回 0 也回退 lsof | 只有返回 -1（不可用）才回退 |
| history_add 每次落盘（~21.9ms） | fputs+fclose 的 FS 延迟 | 内存缓冲 32 条 + 2s/退出时刷盘；读前先刷盘 |
| TCP Nagle | 响应头/体两次小写入等 ACK | accept 后设 TCP_NODELAY |

### 不丢覆盖：maps_hit()
lsof 原本能抓「mmap 了文件但已关 fd」的进程（/proc/<pid>/fd 看不到）。
现在 `proc_scan` 读 `/proc/<pid>/maps` 做子串匹配，同样能抓到，
且能读出映射权限显示成「只读映射/读写映射」。实测用 C 程序 mmap+close(fd) 验证通过。

### 顺带修的真 bug
1. **历史 200 条截断从未生效**：`if (buf[strcspn(buf,"\n")]) continue;`
   对以 \n 结尾的正常行恒为真 → 所有行都被跳过 → `lines` 恒为 0 → 文件无限增长
   （实测已 652 行）。改按 `buf[bl-1]=='\n'` 判断完整行，现在截断到 200 行
2. `/api/scan` 的 conclusion 还是「关闭它们即可解除占用」——上一轮只改了 CLI 和界面，
   漏了 API。已按平台/可删与否分流

### 实测数据
| 场景 | 优化前 | 优化后 |
|---|---|---|
| 单文件扫描 (HTTP) | 120~165 ms | **1.0 ms** |
| 目录深扫 (HTTP) | 370 ms | **0.9 ms** |
| 批量 20 项 (HTTP) | 2506 ms | **34 ms** |
| history_add | 21.9 ms | **1.3 ms** |
| GET /api/health（协议层） | — | 0.09 ms |

## 教训
- **“扫不到就回退到重武器”是隐形性能杀手**。lsof 是兜底不该是常规路径；
  原生 /proc 扫描已经覆盖 fd + cwd/exe，缺的只是 mmap，补上即可彻底甩掉 lsof
- **小文件的频繁 append 在某些文件系统上很贵**（这里是 overlay，单次 ~20ms）。
  日志/历史这类非关键写入一律走缓冲 + 批量落盘
- **性能优化必须先测量再动手**：这次从 120ms 到 1ms，靠的是四步隔离，
  而不是猜。裸 socket 对照那一步最关键——它把“协议层 vs 业务层”一刀切开
- 大段替换 edit 一定要 grep 关键调用点（今天又踩一次，history.c 里
  helper 插在定义之前导致 static 声明冲突，编译器直接报出来了）
