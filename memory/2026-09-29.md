## 本轮二：诊断结论按平台语义修正（commit 8ea0d0a + UI）
**发现的误导性结论**：Linux/macOS 上发现占用进程就给“关闭它们即可解除占用”，
但 POSIX 语义下 unlink/rmdir 根本不看谁开着文件——`tail` 只读占着文件，`rm` 照样删得掉。
旧结论把用户引向“去杀进程”，而真因是权限/只读挂载/不可变标志/目录非空。

改动：
- `diag_posix`：发现占用进程**不再置 restricted**（不再谎报受限）；
  原因写成“正在使用它的进程：xxx (PID n，只读)”+ 明确标注“不阻止删除”；
  对策改成三条真正有用的：释放空间/安全弹出才需要 kill、
  “删了空间没释放是因为句柄还开着（/proc/<pid>/fd 见 (deleted)）”、sudo lsof 查详情
- `print_report` 结论分平台/分场景（Windows 保持原语义；POSIX 区分 文件可删/目录/不可删）
- `diag_windows`：把访问权限翻译成人话——【写】权限的 N 个 = 保存失败的直接原因、
  持【删除】权限的在做删除/改名、全是【只读】时说明不影响读但仍挡删除
- `web/app.js` 结论徽章改用 `canDelete` 判断（跨平台正确）：
  能删 → “🔍 N 个进程正在使用它（不影响删除）”；不能删 → “🔒 N 个进程占用，挡住了删除/改名”

## 经验
